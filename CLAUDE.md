# sex (and sex-lite)

Firecrawl v2 compatible web search (SearXNG) + fetch (Defuddle) as a CLI, HTTP API (Hono + oRPC) and MCP server (`@modelcontextprotocol/server` v2). See README.md for usage.

## Layout

A Bun workspace (`workspaces: ["packages/*", "apps/*"]`; `linker = "hoisted"` in bunfig.toml: one root `node_modules`, which the sex build walks). `packages/` holds libraries, `apps/` the two products; the target structure is `docs/architecture.md` (issue #94), reached step by step; steps 1-7 are done, so `apps/sex` is fully on packages (step 8 is the first npm release).

- `packages/scrape` (`@searxng-js/sex-scrape`, published to npm, imported by name) — `scrapeUrl`, `scrapeUpload`, `assertScrapeCapabilities`, the scrape schemas (`ScrapeRequest`, `Document`, formats, actions...) and the capability interfaces (`ScrapeBrowser`, `ScrapeLlm`, `ScrapeDocs`, `ScrapeCache`, `ChangeTracker`). Depends on sex-egress, sex-page, p-limit, zod and bundles `sex-errors`. Takes its own options (a `ScrapeContext`, never `CoreConfig`), `signal` + `deadlineAt` instead of a `Deadline`, and an optional `logger`. Its tests are `node:test` and run on both Bun and Node. `Deadline` is not exported; it comes from the private `sex-deadline` and is bundled in.
- `packages/search` (`@searxng-js/sex-search`, published to npm, imported by name) — `search`, `searxng` (one SearXNG query), the query operators and the search schemas. Depends on sex-scrape, sex-searxng, p-limit, zod and bundles `sex-errors`. Same rules as sex-scrape; its tests are `node:test` over a mock SearXNG on `node:http`.
- `packages/server` (`@searxng-js/sex-server`, private, Bun only, apps-only, `bun:test`; reached through the `sex-source` condition, subpaths `.` / `./config` / `./engine` / `./log` / `./cli` / `./http/*` / `./mcp/tools` / `./testing`) — what sex and sex-lite share: `BaseEngine`, `CoreConfig` parsing, the stderr logger, the Hono + oRPC app with `/v2/scrape` and `/v2/search`, the `web_fetch` / `web_search` MCP tools and the CLI flags. It is the only place that turns `SEX_*` config into package options (`BaseEngine.settings`, `searxng` options) and hands the logger to the packages. Must not import from `apps/*`, nor depend on browser, LLM, here-docs or job code.
- `packages/testing` (`@searxng-js/sex-testing`, private; `startCountingProxy`, `CERT` / `KEY` also import on Node for the package tests) — fixture site, mock SearXNG, `startCountingProxy` (a forward proxy that records requests; a public IP literal such as `93.184.216.34` passes the SSRF check without DNS and the proxy delivers it to a local fixture), `textPdf`, `waitFor`. `@searxng-js/sex-server/testing` re-exports them and adds `testCoreEngine()` / `testCoreConfig()`; `apps/sex/test/helpers.ts` adds the mock LLM and `testEngine()`. `node:test` package tests start their own `node:http` servers instead.
- `packages/errors` (`@searxng-js/sex-errors`, private, imported by name) — `ERRORS`, `AppError` and the helpers; see the errors entry below. Its tests are `node:test` and run on Node too (`"sexNodeTests": true`, built by `build:packages`).
- `packages/egress` (`@searxng-js/sex-egress`, published to npm, imported by name) — `EgressPolicy`, `safeFetch`, `assertPublicUrl`, `networkError`, `rewriteUrl`, `DEFAULT_MAX_BODY_BYTES`; depends on `ipaddr.js` and bundles `sex-errors`; `undici` is an optional peer (Node only, the transport). Takes its own options (never `CoreConfig`), a `signal` instead of a `Deadline`, and has no logger because it logs nothing. Its tests are `node:test` and run on both Bun and Node.
- `packages/page` (`@searxng-js/sex-page`, published to npm, imported by name) — HTML and PDF extraction: `extractFromHtmlInline`, `PAGE_SCRIPT`, `pdfToMarkdown` / `joinPages`, `ExtractPool` (worker threads) and `markdownToHtml`. Depends on defuddle, linkedom, unpdf and bundles `sex-errors`; `marked` is an optional peer (Node only, see the markdown entry). Takes its own options (`ExtractPool({ size, taskTimeoutMs, logger?, workerUrl? })`), a `signal` instead of a `Deadline`, and a `logger` option (`debug` / `info` / `warn` / `error`; silent without one). Its tests are `node:test` and run on both Bun and Node. `packages/page/scripts/bench-extract.ts` is its benchmark.
- `packages/searxng` (`@searxng-js/sex-searxng`, published to npm, imported by name) — `SearxngService` and `generatedSettings` / `proxiedSettings` / `redactProxy`. Depends on `@searxng-js/searxng` and bundles `sex-errors`; `yaml` is an optional peer (Node only). Takes `SearxngOptions` (`url`, `binaryPath`, `settingsPath`, `proxyUrl`, `logger`), never `CoreConfig`; `packages/server/src/engine.ts` maps `SEX_*` config onto it. Its tests are `node:test` (the fake SearXNG in `test/fixtures` is plain Node) and run on both Bun and Node.
- `packages/browser` (`@searxng-js/sex-browser`, published to npm, imported by name; peer `sex-scrape`) — `BrowserPool` (a `ScrapeBrowser`), `planEgress` / `browserKind`, `EgressProxy`, the request policies (`applyRequestPolicies`), `AdBlockList`, `registerEmbeddedLightpanda` / `registerEmbeddedAdblock` (apps/sex/scripts/build.ts keeps embedding through them). Depends on sex-egress, sex-page, p-limit, puppeteer-core and bundles `sex-errors`, `sex-deadline` and Defuddle's browser bundle (as a string, by a tsdown plugin; `defuddle` is a devDependency). Takes `BrowserPoolOptions` (never `Config`: `apps/sex/src/engine/engine.ts` `browserOptions(config)` maps it) and an optional `logger`. Node-compatible: `node:child_process` (not `Bun.spawn`), a `PATH` walk (not `Bun.which`), `node:zlib` zstd. `scripts/` (`lightpanda.ts`, `adblock.ts`, `bench-adblock.ts`, `bench-egress.ts`) are Bun scripts for maintainers and not published. Its tests are `node:test` (policies, plan, `EgressProxy` against `node:http`, spawn with stand-in binaries); the suites that need a real browser or the engine stay in `apps/sex/test` (`bun:test`).
- `packages/llm` (`@searxng-js/sex-llm`, published to npm, imported by name; peer `sex-scrape`) — `Llm` (a `ScrapeLlm`), `TokenMeter`, the prompts, `splitSegments`, `compileJsonSchema`. Depends on xsai, ajv and bundles `sex-errors`, `sex-deadline`. Takes `LlmOptions` (`endpoint`, `maxInputChars`, `timeoutMs`, `logger`); the auxiliary calls take a `CallTime` (a `Deadline` is one). Its tests are `node:test` over a mock endpoint on `node:http`.
- `packages/docs` (`@searxng-js/sex-docs`, published to npm, imported by name; peer `sex-scrape`) — `DocsConverter` (a `ScrapeDocs`) and `registerEmbeddedDocs`. Depends on here-docs (a git dependency), p-limit and bundles `sex-errors`, `sex-deadline`. Takes `{ enabled, concurrency, logger }`. Whether here-docs runs on Node is here-docs' matter (the README says so); the tests use a stand-in for it.
- `packages/store` (`@searxng-js/sex-store`, published to npm, imported by name; peer `sex-scrape`) — `SqliteScrapeCache`, `SqliteChangeTracker`, `markdownDiff`. Depends on `diff`; no private library. `node:sqlite` and `node:zlib` zstd instead of `bun:sqlite` / `Bun.zstd*` (measured about equal on Bun: see the SQLite risk in `docs/architecture.md`); `src/sqlite.ts` keeps prepared statements per connection (preparing on every call is about half again slower). The on-disk files (`user_version` 1, zstd bodies) are the ones the Bun-only version wrote and must stay readable. Its tests are `node:test`, including opening a legacy-schema file.
- `packages/map` (`@searxng-js/sex-map`, published to npm, imported by name) — `mapSite`, `sitemapUrls`, `fetchRobots` / `parseRobots` / `robotsTextFor`, `normalizeUrl`, the url-filter helpers (`compilePatterns`, `isSkippableFile`, `basePathOf`...) and the map schemas (`MapRequest`, `MapResult`). Depends on sex-scrape, sex-search, sex-egress, zod and bundles `sex-errors` and `sex-deadline`. A `MapContext` is a `SearchContext`; `mapSite` keeps a `Deadline` inside (`expiredCode: "TIMEOUT"`), while `sitemapUrls` / `fetchRobots` take a `CallTime` and rebuild one (`Deadline.of`), so no `Deadline` crosses the boundary. Logs through `ctx.logger`. Its tests are `node:test`; the ones that need a local site with a real engine (`robots-rfc`, `map-hardening`) stay in `apps/sex/test`.
- `packages/jobs` (`@searxng-js/sex-jobs`, published to npm, imported by name) — crawl, batch scrape and extract (`startCrawl`, `startBatchScrape`, `startExtract`, `runTask`, `abandonTask`, `startWorker`), `JobStore` / `SqliteJobStore`, `TaskQueue` / `MemoryTaskQueue`, `JobScheduler`, `DocumentLog` and its backends, webhooks, and the schemas of the job endpoints and `parse`. Depends on sex-scrape, sex-map, sex-egress, p-limit, zod and bundles `sex-errors` and `sex-documents-s3`; `@aws-sdk/client-s3` is an optional peer (Node only, for `s3://` documents). Everything that took sex's `Engine` takes a `JobsContext` (`src/context.ts`): a `MapContext` plus `jobs` (`JobBackend`: store, queue, scheduler), `jobSettings` (`concurrency`, `extractWildcardPages`, `webhookSecret`), `search(req, signal)` and an `llm` that satisfies `JobsLlm` (sex-llm's `Llm` does; it gained `schemaErrors` and `relevanceFieldDescription` for it, so jobs needs no import of sex-llm). Takes its own options everywhere (`createDocumentLog({ documentsUrl, dataDir })`, `new SqliteJobStore(path, ttlMs, log, logger)`), never `Config`; logs through `ctx.logger` / the `logger` argument. `SqliteJobStore` is on `node:sqlite` through `src/db.ts` (prepared statements per connection, `BEGIN IMMEDIATE` transactions): measured on Bun 1.4.3 against `bun:sqlite` it was within about 1.1x (see the SQLite risk in `docs/architecture.md`), and an existing `jobs.sqlite` opens unchanged. No `Deadline`: a webhook attempt and the crawl's robots.txt fetch use `AbortSignal.timeout` at their entry, an extract's LLM calls get `{ signal }`. Its tests are `node:test` (memory queue, scheduler, store, extract merging, and batch / crawl / webhook on a memory queue over `node:http`); the Engine-level job tests (`scheduling`, `settlement`, `dead-letter`, `webhook`, `store-contract`, `durability`...) stay in `apps/sex/test` on `bun:test`.
- `packages/documents-s3` (`@searxng-js/sex-documents-s3`, private, `sexNodeTests`) — `S3DocumentLog` and `openS3`, bundled into sex-jobs (which re-exports both). `openS3` is `Bun.S3Client` when `typeof Bun` is defined, else a dynamic import of `@aws-sdk/client-s3` (optional peer of sex-jobs; the missing package is a `NOT_SUPPORTED` error that says to install it). The interface it implements (`DocumentLog`) lives in sex-jobs, so the log is structurally typed and imports nothing from it. Object names are `<jobId>/<crypto.randomUUID()>.json` (random, not time-ordered: nothing may rely on listing order). A range past the end of an object reads as empty on both clients. `SEX_TEST_S3_URL` runs its `s3.test.ts` live on Bun and Node.
- `packages/deadline` (`@searxng-js/sex-deadline`, private, imported by name) — `Deadline` and `CallTime`, bundled into sex-scrape, sex-map, sex-browser, sex-llm and sex-docs (a plugin cannot import it from sex-scrape, which does not export it; each bundle has its own class, so `Deadline.of(time)` rebuilds one from `signal` + `deadlineAt` even when `time` is another bundle's `Deadline`). The apps import it too. Its tests are `node:test` (`"sexNodeTests": true`).
- `apps/sex` — the full product: sex-server plus sex-browser, sex-llm, sex-docs, sex-store, sex-map and sex-jobs composed from its `Config` (`engine/engine.ts`; `engine/jobs/index.ts` builds the job backend: `SqliteJobStore` + the bunqueue `TaskQueue` in `engine/jobs/queue.ts`, which only this app uses). `Engine` is the `JobsContext` (`jobs`, `jobSettings`, `search`, `llm`).
- `apps/sex-lite` — search + fetch only (`src/cli.ts`, `src/server.ts` for the HTTP app and its two MCP tools, `src/engine.ts` for `liteEngine`, which is a `BaseEngine` whose 501 hints point at sex). It depends only on sex-server, sex-scrape and sex-search; keep it to those plus wiring, a feature that needs more belongs in sex.

Files:

- `packages/server/src/engine.ts` — `BaseEngine`: SearXNG, extract pool, scrape limit, `scrape` / `search` / `warmup` / `describe` / `close`; it is a `SearchContext`, a plain object built from `settings` (`ScrapeSettings`: `allowPrivateNetwork`, `proxyUrl`, `stealthProxyUrl`, `userAgent`, `timeout`, `maxBodyBytes`, mapped from `CoreConfig`) and `logger` plus the pieces below. sex's `Engine` (`apps/sex/src/engine/engine.ts`) extends it and overrides `browser` / `llm` / `docs`. `close()` chains stay hand-written (`Symbol.asyncDispose` / `AsyncDisposableStack` from the design doc is not adopted yet: the order of the chain matters and each app overrides it).
- `packages/scrape/src/capabilities.ts` — the interfaces a scrape uses for the optional capabilities (`ScrapeBrowser`, `ScrapeLlm`, `ScrapeDocs`, `ScrapeCache`, `ChangeTracker`) and `GUARD_MAX_CHARS`. `scrapeUrl` / `search` take a `ScrapeContext` / `SearchContext` (`packages/scrape/src/scrape.ts`: intersections of small interfaces `Fetcher` (`settings`, `scrapeLimit`), `Extractor` (`extractPool`), `ScrapeCapabilities` and `ScrapeExtras` (`missingHints`, `logger`); any `BaseEngine` fits, none is required); a capability is used only when present and `enabled` (the browser enforces the egress rules itself, `BrowserScrapeOptions` has no guard), otherwise `browserRequired()` / `llmRequired()` with the context's `missingHints`. Time crosses these interfaces as `CallTime` (`signal` + optional `deadlineAt`, see the deadline entry), never as a `Deadline`; an implementation that needs a `Deadline` makes its own with `Deadline.of(time)` (apps/sex does, in browser, docs, llm and the change tracker).
- `packages/server/src/cli/common.ts` — flags (`coreArgs`, `httpArgs`, `searchArgs`, `fetchArgs`), `coreOverrides`, `runSearch` / `runFetch`, `engineOrExit`, `warmupOrExit`, `onShutdown`, `listenAddress`. `apps/sex/src/cli.ts` and `apps/sex-lite/src/cli.ts` are citty CLIs (`search`, `fetch`, `serve`, alias `http`) built from them. There is no separate worker process: sex's `serve` runs crawl/batch/extract tasks itself.
- `packages/server/src/config.ts` — zod-validated `CoreConfig` (`resolveCoreConfig`, plus `CORE_FIELDS` / `parseFields` / `coreConfigFrom` for products that add settings); `apps/sex/src/config.ts` extends it (`resolveConfig`; `SEX_WEBHOOK_SECRET` has no CLI flag, so the key stays out of the process list). Precedence: CLI flag → `SEX_*` env → default (sex-lite reads the same `SEX_*` names; `SEX_PROXY_URL` and `SEX_STEALTH_PROXY_URL` are env only, like `SEX_WEBHOOK_SECRET`, and `parseFields` never echoes them back). Empty values count as unset; invalid values throw `CONFIG_INVALID`. Tests pass an explicit env object instead of `process.env`.
- `packages/errors/src/index.ts` (`@searxng-js/sex-errors`) — the `ERRORS` catalog (every error code with its HTTP `status`, `retryable`, `fallback` and `blocked`) and `AppError`, which takes its status and hints from it at construction and copies them (`status`, `retryable`, `fallback`, `blocked`) onto the instance: `new AppError("CODE", message, details?)`. New codes go in the catalog first. `AppError` carries a `Symbol.for("searxng-js.sex.error")` marker; check errors with `AppError.isInstance(e)`, never `instanceof` (another bundled copy of the class is not the same class). The marker name and the instance fields are a contract between versions. Everything that judges an error reads the instance fields, never looks the code up in the catalog again. Deterministic failures are never 502/503 (the SDK retries those); only `*_UNAVAILABLE` and upstream errors (`LLM_ERROR`, `SEARCH_BACKEND_ERROR`) are. An LLM endpoint's 4xx (bad key, wrong model) is `LLM_REQUEST_REJECTED` (500). `fallback` says whether a failed browser scrape may be answered over plain HTTP: `scrapeInner` does that (sequentially, within the scrape's remaining deadline, at least `FALLBACK_MIN_MS`; never with actions) and also when the browser renders a 2xx page with empty markdown; the document's `warning` says so. `blocked` + `BLOCKED_STATUSES` (403, 429) are the one rule for "the site turned the bot away; another proxy may help" (`isBlocked(status | AppError)`, judged by the error's `blocked` field, never by its own 403): `scrapeInner` retries once through `SEX_STEALTH_PROXY_URL` (`config.stealthProxyUrl`) when it is set. The retry is in `fetchBody` (plain fetch, also the browser fallback and the empty-page fetch) with the scrape's own `Deadline` and only with at least `FALLBACK_MIN_MS` left, and after a browser page with a blocked status (never with actions; the retry replaces the browser's page only if it is not blocked). `proxy: "basic"` never retries; `proxy: "stealth"` starts with the stealth proxy over plain HTTP (no browser; actions are a 400); `metadata.proxyUsed` / the `warning` say `stealth`. Same SSRF path as `SEX_PROXY_URL` (it is the `proxy` field of `safeFetch`). A new error code that a different egress address can fix sets `blocked` in the catalog, not a check at the call site. Helpers: `badRequest`, `unsupported`, `browserRequired`, `llmRequired`. Throw these, not plain `Error`s.
- `packages/server/src/log.ts` — leveled logger, stderr only; the apps' logger, passed to the packages as their `logger` option (they are silent without one). Code in `apps/` and `packages/server` imports it; a package never does.
- `apps/sex/src/engine/` — sex's engine on top of sex-server: `engine.ts` composes the packages above (browser, LLM, documents, stores, map, jobs) from `Config`; `jobs/` holds the app's job backend and its bunqueue queue
- `packages/deadline/src/index.ts` (`@searxng-js/sex-deadline`, private) — `Deadline`: the time one scrape has left plus the caller's cancellation. Created once at the top (`Deadline.start(ms, { signal })`, `Deadline.unbounded(signal)`, or `Deadline.of(callTime)` for a call that arrives with a `CallTime`) and passed down; steps use `signal`, `remaining()`, `slice(ms)` for a step budget of their own, `sleep`, `bound(promise)` for work that ignores the signal, and `translate(err)`, which turns anything thrown after the abort into `SCRAPE_TIMEOUT` (time ran out) or `TIMEOUT` (caller cancelled). Timeout vs cancel is read from `signal.reason`: a `TimeoutError` is the time running out, anything else a cancel. Inside a package never build `AbortSignal.timeout` / `AbortSignal.any` in a step; at a package boundary only an `AbortSignal` goes in and, where the receiver wants a number (puppeteer's `timeout`, the docs converter's "90% of what is left", the diff cap), a `deadlineAt` (epoch ms): that pair is `CallTime`, `deadline.time()` makes one, and a package's entry may merge its own timeout (`search` does: `AbortSignal.any` of the caller and its timer, with its own `TIMEOUT` errors). An error built from a `CallTime` says "Timed out ..." without a duration, since only the owner of the time knows it. Only the packages that bundle it use the class (map keeps one inside `mapSite`); the apps and sex-jobs do not. `scrapeUrl` cuts `timeout` for the whole scrape (fetching, rendering, extracting and the LLM calls; no `timeout` with LLM formats or the guard means `max(settings.timeout, 60 s)`, see `scrapeTimeout`); each LLM call gets `min(SEX_LLM_TIMEOUT, what is left)`. Extract jobs scrape with `llmOutsideTimeout`, so their guard calls are cut from the job's deadline instead.
- `packages/page/src/markdown-html.ts` (`@searxng-js/sex-page`) — `markdownToHtml` (async): `html` / `rawHtml` of a converted document (PDF, office file, CSV) is its Markdown. `typeof Bun` → `Bun.markdown.html` (raw HTML escaped via `noHtmlBlocks` / `noHtmlSpans`); otherwise the optional peer `marked` (GFM on, its `html` renderer escapes block and inline raw HTML; chosen over markdown-it, which needs a plugin for task lists, and micromark, which needs the GFM extension packages: one package, no dependencies), and a missing `marked` is a `NOT_SUPPORTED` error that says to install it. `packages/page/src/pdf.ts` extracts page by page and stops at `maxPages` (`numPages` = extracted, `totalPages` = in the file; the docs path reports the same pair). Both paths return the pages one by one (`PdfText.pages` / `DocsResult.pages`, `PdfPage`), and `scrapeInner` builds `Document.pages` (`parsers[].pages`) and the `pageMarkers` text from them with `joinPages`; a converter that returns text belonging to no page gets `pages: undefined` and a warning instead. `mode` / `blocks` / `refresh` are still ignored (here-docs does not say which pages it OCR'd, nor take an OCR switch).
- Options that cannot be honoured are refused or reported, never dropped: `assertSupportedOptions` (501 for `redactPII` / `zeroDataRetention` / `onlyCleanContent`, 404 `SCRAPE_NO_CACHED_DATA` for `lockdown` / `minAge`, 400 for `rawBase64` combinations and `fastMode` + actions) and `ignoredOptionWarnings` (Firecrawl's "-- your scrape may be partial") in `scrape.ts`; search does the same for `tbs` / `country` / `location` in `search.ts`. A new option that has no effect goes into one of those two, and into the README's differences list. `rawBase64` returns before the browser and extraction (`safeFetch` only); `fastMode` makes `scrapeInner` treat the browser as absent. `SEX_STRICT_REQUESTS` (`strictRequests`) makes `procedureBase` reject undeclared body fields (nested objects too) with 400; MCP is not covered.
- `packages/egress/src/net.ts` (`@searxng-js/sex-egress`, published; imported by package name, with `fetchWithin` in `packages/scrape/src/fetch-within.ts` (and sex-map's copy in `packages/map/src/fetch-within.ts`) for a `Deadline`) — `networkError(err, url)` names a failed fetch (Bun/Node `code`, Chromium `net::ERR_*`, Lightpanda's libcurl names) as `SCRAPE_DNS_RESOLUTION_ERROR` / `SCRAPE_SSL_ERROR` / `SCRAPE_SITE_ERROR` / `FETCH_FAILED`; `safeFetch` and the browser both use it. `safeFetch` takes a `signal` (`FetchOptions.signal`), not a `Deadline`: when it aborts it throws `SCRAPE_TIMEOUT` (the reason is a `TimeoutError`) or `TIMEOUT` (cancelled), and scrape / map call it through `fetchWithin(url, deadline, opts)`, which replaces whatever it threw by `deadline.translate` (so a slice's `expiredCode` still applies). `sendRequest` is the transport: on Bun `fetch` with its `proxy` / `tls` options (a pinned request is addressed to the IP with `pinToAddress`, host in `Host` and the TLS server name); on Node always undici (dynamic import, optional peer of sex-egress, a devDependency for its tests; missing = `NOT_SUPPORTED` naming `undici`), where a pinned request keeps its URL and the per-request `Agent`'s `connect.lookup` answers with the validated address (Host, SNI and the certificate check use the real name), `skipTlsVerification` / `ca` go into the connect options and a proxy is a `ProxyAgent` (same semantics as Bun; http targets are forwarded, https tunnelled). Each request owns its dispatcher, closed when the response body ends, is cancelled or fails, or the signal aborts (`closeWithBody`); `networkError` reads the code from undici's `err.cause`. The app builds pass `--external undici` (never imported on Bun). `safeFetch` re-checks every redirect hop through `EgressPolicy` and connects to the DNS-validated IP so a second lookup cannot rebind. `FetchOptions.proxy` (`config.proxyUrl`, `SEX_PROXY_URL`) is a required field, so a new call site must decide: with a proxy the request goes through Bun `fetch`'s `proxy` option (Node: undici `ProxyAgent`) and is **not pinned** (the proxy resolves the name); the host is still resolved and checked before every hop, and a name that does not resolve locally is refused (`requireResolvable`), since the proxy's resolver could know an internal name. Caller-set `Proxy-Authorization` / `Proxy-Connection` are dropped. Rebinding between check and the proxy's lookup is the proxy's to stop (README, "出站代理"); never claim pinning for proxied requests. The proxy URL carries credentials: no CLI flag, redacted in config errors. LLM and S3 deliberately do not use it (operator-set addresses; the README says to use Bun's `HTTP(S)_PROXY` + `NO_PROXY` there, which was measured). The managed SearXNG does: `searxng-settings.ts` `generatedSettings` appends `outgoing.proxies` to the package's default settings only when sex owns the settings (no `SEX_SEARXNG_URL`, no `SEX_SEARXNG_SETTINGS`); the file is `0600`, deleted once SearXNG is up, and its output goes through `redactProxy` before a log or error message.
- `packages/egress/src/egress.ts` (`@searxng-js/sex-egress`) — `EgressPolicy`: **the** outbound rule, defined once. `resolve(url, requireResolvable)` resolves the host, refuses (`PRIVATE_NETWORK_BLOCKED`) when any address is not global unicast (`isPrivateIp`: loopback, private, link-local incl. metadata `169.254.169.254`, ULA, IPv4-in-IPv6 unwrapped; `localhost` / `*.localhost` by name) and returns the addresses to connect to (empty for an IP literal, when `allowPrivateNetwork`, or an unresolvable name; `requireResolvable` refuses that last case, used whenever something else will resolve the name). Answers are cached per host for 30 s (5 s for a name that did not resolve; bounded), so subresources of one page cost one lookup and a changed record is noticed soon. `egressFor(allowPrivate)` is the shared per-mode instance; `assertPublicUrl` (net.ts) and `safeFetch` use it, the browser's enforcement points get it from `BrowserPool`. The rule lives here only: an enforcement point asks it, it never re-implements the checks. Tests inject `resolver` / `now`.
- `packages/page/src/extract-pool.ts` + `packages/page/src/extract-worker.ts` (`@searxng-js/sex-page`) — HTML/PDF extraction in a worker-thread pool (`SEX_EXTRACT_WORKERS`, 0 = main thread), on `node:worker_threads` so it runs on Bun and Node. `ExtractPool` takes an `AbortSignal` per job (a `TimeoutError` reason is `SCRAPE_TIMEOUT`, anything else `TIMEOUT`); `packages/scrape/src/extract-within.ts` (`extractHtmlWithin` / `extractPdfWithin`) hands it a `Deadline`'s signal and translates what it throws, like `fetchWithin`. The worker is a second tsdown build (`dist/extract-worker.js` beside `dist/index.js`, found through `import.meta.url`; the config also turns the `page-script.js` text import into a string module, since Node cannot do `with { type: "text" }`). `bun run build` embeds the worker as an extra entrypoint.
- `packages/jobs/src/crawl.ts` `crawlParamsFromPrompt` maps the site first (`mapSite` with the sex-only `skipSearch`, `filterByPath: false`, limit 50, 15 s) and gives the URLs to `crawlOptions` as `site_urls`; a failed map or a start URL alone means the prompt alone. Its tokens are not counted (a crawl job does not exist yet, and has no `tokensUsed`).

- `packages/browser/src/browser.ts` (`@searxng-js/sex-browser`) — `BrowserPool`: `scrape` takes the scrape's time as `signal` + `deadlineAt` (`BrowserScrapeOptions extends CallTime`; it makes a `Deadline` with `Deadline.of`), and waiting for a slot, load, `waitFor`, actions and the page script all run inside it; the page's context is closed when it ends. CDP connections to a Lightpanda child process (`--lightpanda`) or an external browser (`--cdp-url`). The child is spawned lazily, spawned again after it exits, and not respawned for a cooldown after repeated failed starts (`BROWSER_UNAVAILABLE`). On Linux with `setpriv` it runs as `setpriv --pdeathsig TERM -- lightpanda serve ...` so it dies with sex even on SIGKILL (no equivalent on macOS; plain spawn otherwise), and gets `--block-private-networks` unless private networks are allowed **or `SEX_PROXY_URL` is set** (the flag refuses the loopback `EgressProxy` too, which then does the checking). No proxy flag or credentials on its command line. `BrowserPool` is the only place that knows which enforcement a browser gets (next two bullets); `scrapeUrl` passes no guard. `BrowserPoolOptions`' `kind` / `policy` / `adBlockList` are for tests and the benchmark.
- `packages/browser/src/browser-egress.ts` — **where the outbound rules are enforced, per browser** (`browserKind`, `planEgress`; README has the same table). The rules are `EgressPolicy`'s; browsers differ in where they can be enforced: 

  | browser | SSRF | ads | credentials / media |
  |---|---|---|---|
  | Lightpanda (spawned) | `--block-private-networks` (behind `SEX_PROXY_URL`: `EgressProxy`) | CDP | CDP, when needed |
  | Chrome on this machine (`--cdp-url` host is loopback) | `EgressProxy` | `EgressProxy` | CDP, when needed |
  | Chrome elsewhere (`--cdp-url`) | CDP `requestGuard` (asks `EgressPolicy` per origin) | CDP | CDP, when needed |

  "When needed" = interception is on only if a policy wants it (credentials, `SEX_BLOCK_MEDIA`, the guard, CDP ads). A `--cdp-url` browser is assumed to be Chrome (credentials answered via `page.authenticate`; Chrome ignores credentials in the proxy URL and fails closed with `ERR_NO_SUPPORTED_PROXIES`); Lightpanda takes them in the `proxyServer` URL, because it never answers a CONNECT 407. A remote browser behind `SEX_PROXY_URL` talks to the proxy itself (`contextProxy`, per-context `proxyServer`) with the guard still in front. With `allowPrivateNetwork` no path checks anything. A new rule or enforcement point goes into `planEgress` and gets a case in its tests, not an `if` in `scrapeInner`.
- `packages/browser/src/egress-proxy.ts` — `EgressProxy`: forward proxy on `127.0.0.1:<random>` (`node:http` `createServer` + `connect` event; no proxy library, no hand-written HTTP parsing), lazy-started by `BrowserPool`, closed by `engine.close()`. `open(session)` gives a lease per scrape / browser context: random username + password (`Proxy-Authorization: Basic`, `timingSafeEqual` on SHA-256 digests), the session's policy (`adBlock` list + page URL, `upstream`), failure memory (`failureOf(host)`: `refused` | `dns`, which `BrowserPool` turns into `PRIVATE_NETWORK_BLOCKED` / `SCRAPE_DNS_RESOLUTION_ERROR` for a refused main document), `adsBlocked()`; `close()` destroys the lease's sockets. Every request first passes the session's ad list (by host; the page's own host never) and `EgressPolicy.resolve`, then: CONNECT → `net.connect` to the validated IPs in order (first to accept wins, at most `MAX_PINNED_ADDRESSES`), 200, two `pipeline`s; plain http → `http.request` to the validated IP with the original `Host`, hop-by-hop, `Connection`-named and `Proxy-*` headers dropped both ways, redirects passed on untouched. With `upstream` (`SEX_PROXY_URL`) the request is chained (absolute-form with the upstream's credentials, or CONNECT to it) and cannot be pinned: checked once locally with `requireResolvable`, same semantics as `safeFetch` behind a proxy; never claim pinning there. Own answers carry `x-sex-egress: refused | dns | ad | upstream | auth | bad-request`. 60 s idle timeout, 10 s connect timeout. `localhost` / private / metadata targets must be refused for http **and** CONNECT with zero connections to the target: `packages/browser/test/egress-proxy.test.ts` (no browser) and `apps/sex/test/egress-browser.test.ts` (`SEX_TEST_CDP_URL`) hold that line. Nothing may depend on a class or function name (`apps/sex/test/egress-proxy-minified.test.ts` runs a minified bundle; it needs `Bun.build`, hence not in the package).
- `packages/browser/src/browser-policy.ts` — request policy pipeline for the browser path. A `RequestPolicy` decides per request: continue, change headers, or abort; `RequestPolicyPipeline` runs them in order and interception is on only when one is active. `applyRequestPolicies(page, opts)` is the one place that sets user headers/cookies and attaches the handler: `PrivateNetworkPolicy` (the CDP request guard, used only for a remote browser: `BrowserPool` builds it from `EgressPolicy`; per-origin verdict cache, records refused main-frame navigations) and `OriginScopedCredentialsPolicy` (`Authorization` / `Proxy-Authorization` only on the target's origin; `Cookie` goes to the cookie jar as host-only cookies; with `viaProxy` the caller's `Proxy-Authorization` is dropped, it can only be meant for the proxy). New request behaviour is a new policy in the `policies` list of `applyRequestPolicies`, not code in `browser.ts`. `MediaBlockPolicy` (`SEX_BLOCK_MEDIA`: image / media resource types) and `AdBlockPolicy` (`blockAds`, below; CDP route only, the `EgressProxy` blocks ads by host on a local Chrome) come first, so a blocked request never costs the private-network policy a DNS lookup; both are `optional`: on a browser that cannot intercept they are dropped instead of failing the scrape (only the SSRF guard and credentials policies are safeguards). Neither ever blocks a main-frame navigation. `applyRequestPolicies` returns `adsBlocked()`, which `BrowserPool` puts in `BrowserScrapeResult.adsBlocked`. The handler never passes `cookie` back to the browser (Lightpanda 1.0.2 reports it one character short).
- `packages/browser/src/adblock.ts` + `packages/browser/scripts/adblock.ts` — `blockAds` (request option, default true: `scrapeUrl` passes `options.blockAds ?? true`; browser only). The EasyList + EasyPrivacy domain table is derived by the script from a pinned easylist/easylist commit (`EASYLIST_COMMIT`) and checked against `ADBLOCK_TABLE_SHA256`; only `||domain^` (optionally `$third-party`) and `@@||domain^` rules are kept, as lines `domain` / `~domain` (third-party only) / `@domain` (exception). Like Lightpanda it is embedded zstd-compressed by `build.ts` (`registerEmbeddedAdblock`) and from source derived into `$XDG_CACHE_HOME/sex-build` on first use (a table that cannot be had logs a warning once and means no blocking; the script is not in the published package, so there the app passes `adBlockList` or calls `registerEmbeddedAdblock`, and without either `blockAds` does nothing). `loadAdBlockList(logger?)` parses it into three Sets on first use; `AdBlockList.blocks(host, pageSite)` walks the label suffixes, an exception winning over any block rule; `AdBlockPolicy` (CDP) and `EgressProxy` (host) both call it. New rule kinds (URL paths, wildcards, options) need a different matcher behind the same `AdBlockPolicy`, not more cases in the Sets. Upgrading: change `EASYLIST_COMMIT`, run `bun packages/browser/scripts/adblock.ts`, put the printed hash in `ADBLOCK_TABLE_SHA256`. EasyList is GPLv3 / CC BY-SA 3.0; the README names source and licence. `packages/browser/scripts/bench-adblock.ts` measures the cost against a real Lightpanda (`overhead`, `pages`, `cold`).
- `packages/jobs/src/scheduler.ts` — `JobScheduler` (`ctx.jobs.scheduler`): the one way a task gets into the queue (never `queue.add` from a handler), and the place that decides order and pace. crawl-start / extract have no lane and are served before any lane; a page task waits in its job's lane (`Lane { id: jobId, cooldownMs }`); lanes are served in turn, so a big batch cannot starve a small job. `pageLimits(options)`: `maxConcurrency` caps the lane, `delay` makes the cap 1 and sets `cooldownMs`, the quiet time *after a page finished*. It never re-queues a task: the queue skips a capped or cooling lane instead of taking tasks out and putting them back, so a task keeps one taskId and one queue entry and the `settle` / `pushDocument` / outbox rules above need no extra case. A handler returns `TaskOutcome` (`runTask`): "skipped" (job already finished) starts no cooldown. A new kind of task gets a case in `laneOf` (its own lane, `delayMs` for the backoff, a new `TaskEffect`) and goes through `scheduler.add`; webhook deliveries are one: a single `webhook` lane for all jobs, capped at `WEBHOOK_CONCURRENCY` (a lane's cap stays stored in the queue until removed, so per-job lanes would leak caps). `release(jobId)` runs when a job's last task settles. Not in the store: there are no reserved time slots (`next_slot_at`, `slots`, `outbox.run_at` are dropped on open).
- `packages/jobs/src/types.ts` + `sqlite.ts` + `memory-queue.ts`, and `apps/sex/src/engine/jobs/queue.ts` — `JobStore` + `TaskQueue` interfaces. `SqliteJobStore` (`sqlite.ts`, node:sqlite) keeps job state; `MemoryTaskQueue` (in the package) keeps tasks in memory with the same lane / cap / cooldown / delay rules and no redelivery; `BunqueueTaskQueue` (`apps/sex/src/engine/jobs/queue.ts`, the app's) runs tasks on bunqueue's embedded broker; a lane is a bunqueue group (`groupId`), `capLane` a stored per-group concurrency override (it applies only because the worker passes a default `group.concurrency`), a cooldown the broker's `worker.rateLimitGroup`, called on the `completed` event (not inside the handler, where it re-runs the job). Tasks without a group are served first, then groups in turn; bunqueue `priority` only orders within a group, so it is not used. The redelivery rules are tested by delivering a task twice (`scheduling.test.ts`, `settlement.test.ts`). Both use files under `SEX_DATA_DIR` (`jobs.sqlite`, `queue.sqlite`; `serve` defaults to `$XDG_DATA_HOME/sex`) or `:memory:` without one (tests, one-shot CLI). `packages/jobs/src/tasks.ts` dispatches tasks to the crawl/batch/extract handlers (`startWorker(ctx)` wires a queue to them). A task interrupted by a crash is redelivered after a restart (bunqueue's startup recovery counts it as an attempt and dead-letters the task at `attempts`, so `BunqueueTaskQueue` sets `attempts: MAX_DELIVERIES` and its worker wrapper swallows handler errors so a throw is not retried; `attempts: 1` meant no redelivery, #75). A task interrupted `MAX_DELIVERIES` times ends in bunqueue's DLQ, and recovery emits no event for that, so `startWorker(handler, onAbandoned)` reads the DLQ once at start (`getDlqAsync`) and passes each task to `abandonTask` (`tasks.ts`), then `removeDlqJobAsync`; an entry is removed only after `abandonTask` returned. `abandonTask` does what the handler's exit would: a page is failed through `taskEffects.failure` and settled, a crawl start or an extract fails the job (#78), so every side effect of a task is claimed once per `(job, taskId, effect)` in the `task_effects` table: `settle`, `pushDocument` (returns whether the document was new; `countCompleted` increments `completed` in the same transaction), `pushError` (`dropFromTotal`: a failed page leaves `total` in the same transaction; `completed` counts stored documents only, never failures), `claimEffect` (the crawl `started` webhook) and `claimSeen` (a page's redirect target: a redelivery that finds the mark it made itself carries on instead of dropping the page). Handlers go through `taskEffects(ctx, job, taskId)` in `packages/jobs/src/effects.ts` (`page` / `failure` / `started`), which sends the `page` webhook only for a new document; do not call `pushDocument` or `sendWebhook("page")` from a handler directly. Crawl discovery goes through `store.schedule` (seen, robots-blocked, `scheduled` / `total` / `pending` and one `outbox` row per page task, in one transaction); the task queues its rows and then calls `released`, and a redelivered task queues what its crashed delivery left (`outbox(job, owner)`), under the same taskIds. A duplicate delivery's document bytes are orphans (never indexed, so never read; cut off on open if at the end of a JSONL file).
- `packages/jobs/src/webhook.ts` — webhooks. `sendWebhook(ctx, job, event, data?, error?)` (async, never throws; call it through `taskEffects` / `settleTask` / the job's own finish, not for page events directly) builds Firecrawl's payload (`success`, `type: <kind>.<event>`, `id`, `webhookId`, `data`, `metadata`, `error`) and queues a `webhook` task through the scheduler; `deliverWebhook` (run by `runTask`) is one attempt: it claims the `webhook` effect for its taskId (a task delivered twice POSTs once), POSTs through `safeFetch` (10 s) with `X-Firecrawl-Signature: sha256=<hmac>` when `jobSettings.webhookSecret` (`SEX_WEBHOOK_SECRET`) is set (`node:crypto`; the schema rejects that header in a request's `headers`), and on a network error, 5xx, 408 or 429 queues the next attempt as a new task (new taskId, same payload and `webhookId`, `delayMs` = 5 s doubling, `WEBHOOK_MAX_ATTEMPTS` = 5). A webhook task is not part of the job's `pending` and never settles. A crash after the claim loses that attempt (no resend). A failed page (`taskEffects.failure`) sends `page` with `success: false`; extract sends `started` (`taskEffects.started`, so extract tasks have a taskId), `completed` (`data: [result]`) and `failed`.
- `packages/jobs/src/documents.ts` — `DocumentLog`: where scraped documents' bytes go (`append` / `read` / `drop`, plus optional `truncate` for logs that append in place). `FsDocumentLog` (one append-only `<jobId>.jsonl` per job, default under `<dataDir>/documents`), `S3DocumentLog` (from `sex-documents-s3`: `Bun.S3Client` or the AWS SDK, one object per document), `MemoryDocumentLog` (no data dir). `createDocumentLog({ documentsUrl, dataDir })` picks one from `SEX_DOCUMENTS_URL` / `--documents-url` (`s3://bucket/prefix`, `file:///path`). The SQLite `documents` table indexes them (`object`, `offset`, `length`, `chars`); `documentsJson` returns a page as raw JSON texts, which the crawl / batch status routes send without parsing (`outputStructure: "detailed"` with a `ReadableStream` body).
- `packages/server/src/http/server.ts` — `createHttpApp` / `serveHttpApp`: the Hono app for one product's `AppSpec` (router, MCP server, name): Host/Origin checks, CORS, `/health`, `/docs`, MCP over HTTP at `/mcp`. `packages/server/src/http/procedures.ts` — `procedureBase<E>()` (AppError → oRPC error) and `coreRoutes` (`/v2/scrape`, `/v2/search`). `apps/sex/src/http/router.ts` adds sex's procedures to `coreRoutes`; the team endpoints (`/v2/concurrency-check`, `/v2/team/queue-status`) read `TaskQueue.counts()` (bunqueue) and the store, never a counter of their own; `apps/sex/src/http/server.ts` wraps the sex-server app as `createApp` / `serveHttp`.
- `scrapeUpload` (`packages/scrape/src/scrape.ts`) is `scrapeUrl` for a file the caller sent: the same `scrapeInner` with `internal.upload` as the response (no `safeFetch`, no browser), a synthetic `file:///<name>` URL so the name picks the converter, `sourceURL` = the file name. `POST /v2/parse` (`apps/sex/src/http/router.ts`, sex only) takes `multipart/form-data` (`file` + `options` JSON string) through oRPC's own `File` input; the size cap is `SEX_MAX_BODY_BYTES` (checked on `File.size`; `serveHttpApp` also sets Bun's `maxRequestBodySize` to it plus 1 MiB).

## Gotchas

- Never pass JS *functions* to `page.evaluate`: Bun's bundler can rename globals like `document` inside them. Pass strings.
- Browser and LLM are optional; features needing them must fail with `browserRequired()` / `llmRequired()` (501).
- Both builds pass `--root <repo root>` and `--conditions sex-source`: the extract worker is an extra entrypoint, and `extract-pool.ts` finds it in the binary at `<root>/packages/page/src/extract-worker.ts` (a missing worker shows up as `EXTRACT_FAILED`; smoke-test `dist/sex-lite fetch`).
- here-docs is `--external` in the bundle. `apps/sex/scripts/build.ts` embeds its runtime closure for the target platform file by file (`with { type: "file" }`, via a generated `apps/sex/src/cli.embedded.gen.ts` that registers them and then imports `cli.ts`). At runtime `packages/docs/src/docs.ts` (`registerEmbeddedDocs`) extracts the files once to `$XDG_CACHE_HOME/sex/docs-<digest>` (native libraries load only from real files) and imports here-docs from there; `--compile-autoload-package-json` is required for that on-disk resolution. From source it imports `here-docs` from node_modules. It resolves to TypeScript source through the `bun` export condition (`customConditions` in tsconfig); there is no `dist/` in a Bun install.
- Content-type checks for "is this markup" use `MARKUP_TYPE` from `@searxng-js/sex-egress` (`packages/egress/src/net.ts`); a bare `/xml/` also matches OOXML office documents.
- The SearXNG binary comes from the per-platform optional dependency `@searxng-js/<os>-<cpu>` (linux-x64 glibc ≥ 2.35, darwin-arm64, win32-x64 only); `bun build --compile` embeds the target's one through the package's literal imports, and it is unpacked to `$XDG_CACHE_HOME/searxng-js/` at runtime. Elsewhere (linux-arm64, musl) `SEX_SEARXNG_URL` is required. `@searxng-js/searxng` is pinned to an exact version. `testEngine()` / `testCoreEngine()` default `searxngUrl` to a dead port so tests never start a real SearXNG; tests that run `serve` as a subprocess must set `SEX_SEARXNG_URL`.
- `dist/sex` embeds Lightpanda: the release pinned by version and per-platform SHA-256 in `packages/browser/scripts/lightpanda.ts` (linux x64/arm64 glibc ≥ 2.35, macOS x64/arm64; none for Windows or musl). `apps/sex/scripts/build.ts` downloads it into `$XDG_CACHE_HOME/sex-build`, checks the hash and embeds it zstd-compressed; `findLightpanda` in `packages/browser/src/browser.ts` uses an explicit `--lightpanda-path` first, then the embedded one (decompressed once to `$XDG_CACHE_HOME/sex/lightpanda-<version>-<hash>/`), then PATH. Compose has no browser service, but the binary being present enables nothing: `SEX_LIGHTPANDA` decides. Same for here-docs and `SEX_DOCS`.
- Screenshots (format and action) and the pdf action are deliberately unsupported (501), even with a browser.
- User-supplied URLs must only be fetched through `safeFetch` / `assertPublicUrl` (or the browser, whose route `planEgress` decides), never with a bare `fetch`. A new outbound path asks `EgressPolicy`; it does not copy its checks.
- Logs go to stderr only (stdout carries CLI output).
- Document seqs are assigned when the index row is written, after `append` resolves, so object names must never depend on the seq. Bytes are written before the index row: on open the store cuts unindexed tails (`truncate`, only for jobs that exist); index rows past the end of a JSONL file are dropped on open. Reads never change the index: documents whose bytes are missing or not a whole JSON object are left out of the page with a warning, since on S3 that can be transient or a configuration problem. Documents are deleted only by job id, for jobs the store deleted itself: the sweep writes a tombstone (`dropped_jobs`) in the same transaction as the job's deletion and removes it after `DocumentLog.drop` succeeds; every sweep (one runs on open) retries the remaining tombstones. Never delete documents because they were found in the bucket or directory, which may be shared, and never delete job rows without a tombstone.
- bunqueue's embedded broker is a process-wide singleton bound to one `dataPath`: every `BunqueueTaskQueue` in a process must use the same path (tests use `:memory:` only; the durability test runs `serve` as a subprocess). Always pass `dataPath` explicitly, or bunqueue reads generic env vars like `DATA_PATH` / `SQLITE_PATH`. `shutdownManager()` runs when the last queue closes. bunqueue is pinned to an exact version (it releases very often); bump it deliberately and rerun the job tests.
- `SEX_REDIS_URL` / `SEX_REDIS_PREFIX` are rejected with `CONFIG_INVALID` (Redis/BullMQ and the `worker` command were removed).
- There is no frontend. HTTP endpoints are oRPC procedures (`coreRoutes` from sex-server plus `apps/sex/src/http/router.ts`) mounted in Hono; don't add a frontend bundle or a second routing layer.
- When settings change, update the README env table and this Layout in the same change.

## Commands

- Use Bun, not Node: `bun <file>`, `bun install`, `bun run <script>`, `bun run test`, `bun check` (type check, not `tsc`).
- `bun install`
- `bun run verify` — `bun check && bun run lint && bun run test`
- `bun run test` is `bun test --conditions sex-source`: the `sex-source` export condition (also in tsconfig `customConditions`, next to `bun`) makes a workspace package resolve to its `src/`; `dev`, `dev:lite` and both build scripts pass it too (bunfig.toml has no setting for it), so run a test file as `bun test --conditions sex-source <file>`.
- `bun run build:packages` (`scripts/build-packages.ts`) runs tsdown for every published package under `packages/` and for the private libraries that set `"sexNodeTests": true` (`sex-errors`, `sex-deadline`, `sex-documents-s3`), `bun run test:node` (`scripts/test-node.ts`) runs `node --test` against their dist over the `*.test.ts` of those packages; apps and apps-only libraries (`sex-server`, `sex-testing`) stay on `bun:test`. Versions: changesets (`.changeset/`, independent; `sex-errors` and `sex-deadline` are versioned with the packages that bundle them because changesets requires it, the apps and apps-only libraries are in `ignore`). CI has a Node 24 job for those; its s3 job also runs `sex-documents-s3`'s live test on Node.
- `bun run format` — Biome write
- Opt-in suites: `SEX_TEST_SEARXNG=1` (the real SearXNG binary, optionally `SEX_TEST_SEARXNG_PATH`; `bun test --conditions sex-source packages/searxng/test/searxng.test.ts`), `SEX_TEST_CDP_URL=http://127.0.0.1:9222` (browser tests against a running CDP browser), `SEX_TEST_LIGHTPANDA_PATH=/path/to/lightpanda` (the same browser tests through the spawn path, plus child process lifecycle tests; `bun test --conditions sex-source apps/sex/test/browser.test.ts`; the spawn tests with stand-in binaries are `packages/browser/test/spawn.test.ts`, no opt-in needed) and `SEX_TEST_S3_URL=s3://bucket/prefix` with `S3_ENDPOINT` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` / `S3_REGION` (the job store contract and durability tests with documents on S3; `bun test --conditions sex-source apps/sex/test/store-contract.test.ts apps/sex/test/durability.test.ts packages/documents-s3/test/s3.test.ts`; after `bun run build:packages` the last one also runs under `node --test`). Locally and in CI an S3 server is SeaweedFS: `docker run -d -p 127.0.0.1:8333:8333 -e AWS_ACCESS_KEY_ID=sex -e AWS_SECRET_ACCESS_KEY=sex-secret chrislusf/seaweedfs:4.48 server -s3 -dir=/data -ip.bind=0.0.0.0` (MinIO no longer publishes images on Docker Hub); buckets are created on first write.
- `apps/sex/test/docs.test.ts` runs the real here-docs engines (`packages/docs/test` uses a stand-in) (installed as a dependency) against fixtures in `apps/sex/test/fixtures/`; it skips itself where here-docs cannot start (e.g. Intel macOS).
- `bun run build` (`apps/sex/scripts/build.ts`) — single binary at `dist/sex`, SearXNG, Lightpanda and here-docs embedded (the first build downloads Lightpanda); `--target bun-<os>-<arch>` for other platforms whose packages are installed
- `bun run build:lite` (`apps/sex-lite/scripts/build.ts`) — `dist/sex-lite`, SearXNG embedded. `docker build --target lite .` builds its image; the default target is sex.
- `bun run dev` / `bun run dev:lite` — run sex / sex-lite from source.
